# DOPAMS ETL3 Name Cleaning — Comprehensive Edge-Case Audit

**Scope:** Audit-only. No source code, database records, migrations, or ETL writes were modified in producing this report. All code references point to the current state of `etl3/` on branch `cctns-ai`. All dataset findings are traceable to `S.No.` values in `DOPAMS_Criminal_Profiles_2026-11-18_16-47.xlsx` (51,123 rows × 34 columns).

**Important caveat on `S.No.`:** this column is *not* a database key. It is generated client-side in the export (`DOPAMS-FE/src/routes/criminal-profile/ExportCriminalProfiles.tsx`, `'S.No.': index + 1`) as the row's position in whatever page/sort order the export query ran in. It is stable and unique *within this one file* — which is all that's needed to trace every example below back to a real row — but it will not line up with the same record in a future export run under a different sort/filter.

## 0. Critical Data-Provenance Finding (read this first)

Before auditing `etl3/enrichment/names.py`, I traced where the exported `Full Name` column actually comes from, because the data quality in the export did not match what the ETL3 code in this repository would be expected to produce. The trace (through `D:\Dopams\Dopams app\DOPAMS-BE` and `D:\Dopams\DOPAMS-FE\DB-schema.sql`) shows:

1. The export's `Full Name` field is `profile.fullName` from the `CriminalProfilesQuery` GraphQL query (`ExportCriminalProfiles.tsx:71`).
2. That query is backed by `criminal_profiles_mv`, a materialized view (`DB-schema.sql:1614`), whose `"fullName"` column is defined as `full_name AS "fullName"` — sourced from the **legacy** `public.persons` table, joined through `public.accused` / `public.crimes` / `public.brief_facts_accused`.
3. `etl3/docs/PHASE_7_DOPAMS_CUTOVER_READINESS.md:7` states explicitly: *"The existing DOPAMS GraphQL application still reads `public.firs_mv` and `public.accuseds_mv` through `DATABASE_URL`. That SQL was not pointed at `dopams_cctns`. **Production cutover was not performed.**"*
4. ETL3's own tables — `persons_unified.full_name`, `person_enrichment.cleaned_full_name` (the actual output of `clean_person_names()`) — live in the enhanced-build database (`dopams_cctns_v2`) and are **not** what the frontend, or this export, reads.

**Conclusion:** this Excel file is a faithful sample of **pre-ETL3, legacy-pipeline accused-name text**, not of ETL3's output. It is exactly the right input to scope ETL3's cleaning rules against (every edge case below is real, unfiltered production text), but it cannot be used to grade ETL3's current output quality — ETL3 has never touched these rows. To compensate, every finding in Section C below that makes a claim about "current behaviour" was verified by **actually executing** `etl3.enrichment.names.clean_person_names()` and `etl3.enrichment.multi_accused.detect_multi_accused()` against the real raw strings pulled from this file (see `etl3_function_outputs.json`, reproduced inline in the catalogue). This is projected/simulated behaviour — grounded in running the real functions against real data — not a guess.

A second, related finding: for every one of the 51,123 rows, `No. of Crimes = 1`, `Status of Accused = "-"`, and `Previously Involved Cases` is byte-identical to `Latest Crime No.`. This means the export is **one row per raw accused-in-one-FIR occurrence**, not a deduplicated person profile (despite the "Criminal Profile" name) — consistent with the legacy schema having no cross-FIR person identity resolution, which is a large part of what ETL3's `persons_unified` + `etl3/identity/person_matching.py` candidate generation exists to eventually provide.

## 1. Execution Trace: Where Names Enter, Get Cleaned, and Get Stored (ETL3 only)

| Step | Component | What happens |
|---|---|---|
| 1. Raw entry | `etl3/sources/v1/adapter.py`, `etl3/sources/v2/adapter.py` → `etl3/merger/*` | CCTNS V1/V2 source observations are merged into `persons_unified` (`full_name`, `name`, `surname`, `alias`, `relative_name`, `relation_type`, …) and `accused_unified`. This is the **only** place raw name text enters ETL3; it is stored as-is, untouched. |
| 2. Per-person cleaning | `etl3/enrichment/runner.py` → `_person_enrichment` → `etl3/enrichment/project.py:person_row()` (line 190) → `etl3/enrichment/names.py:clean_person_names()` | For every `persons_unified` row, `clean_person_names()` is called with `full_name`, `name`, `surname`, `alias`, `relative_name`, `relation_type`. Output (`raw_full_name`, `cleaned_full_name`, `cleaned_given_name`, `surname`, `cleaned_alias`, `relation_type`, `cleaned_relative_name`) is hashed (`input_hash`) and upserted into `person_enrichment` via `etl3/enrichment/persist.py:upsert_rows()`. |
| 3. Multi-accused detection | `etl3/enrichment/multi_accused.py:detect_multi_accused()` | Pure, DB-agnostic function. Takes one `accused_unified`-linked person's `full_name` and returns a confidence-scored parse (`high`/`low`/`none`) with segments. **Not called from `project.py`/`_person_enrichment` at all** — it is only invoked from the separate split stage below. |
| 4. Multi-accused split (optional, additive) | `etl3/enrichment/runner.py:_multi_accused_split()` → `etl3/merger/accused_split.py:build_split_rows()` / `write_split_rows()` | For each un-split `accused_unified` parent, calls `detect_multi_accused()`; if `confidence == "high"`, writes new real `persons_unified`/`accused_unified` rows for each segment (deterministic IDs via `split_child_id()`), marks the parent `split_superseded_at`, and records an audit row in `accused_split_audit`. **Gated behind `ETL3_MULTI_ACCUSED_SPLIT_ENABLED=1` (default off) and migration `018_multi_accused_occurrences.sql` (not applied anywhere in this repo yet)** — i.e., this stage is a complete no-op in the system as currently deployed. |
| 5. Downstream read | `_split_child_records()` (runner.py:911), exposed accused view | Once (4) is enabled and migrated, split children are read like any other accused; the parent is excluded once superseded. Children then flow through the **same, unmodified** `_person_enrichment`/`_accused_enrichment`/AI roster pipeline as any other row — step 4 never writes a cleaned name itself. |
| 6. Identity matching | `etl3/identity/person_matching.py:load_persons()` (line 64-75) | Reads `persons_unified.full_name` directly (**not** `person_enrichment.cleaned_full_name`) plus `relative_name`/`phone_number`, normalizes to lowercase alnum tokens, and generates match candidates. Never auto-confirms; always `status='candidate'`. |

**Idempotency:** confirmed. `clean_person_names()` and `collapse_exact_repetition()` are pure, deterministic, side-effect-free functions — same input always produces the same output. `upsert_rows()` (`persist.py:28`) compares a freshly computed `input_hash` against the stored one and skips the write entirely (`unchanged` counter) when nothing changed, so reruns over unchanged source data never duplicate `person_enrichment` rows or `change_log` entries. The split layer is separately idempotent by construction: `split_child_id()` (`accused_split.py:55`) derives a deterministic id from `(parent_id, segment_index, normalized_segment_text)`, and `diff_superseded_children()` only ever supersedes ids not reproduced by the current run — confirmed by `test_build_split_rows_idempotent_rerun_same_ids` and `test_split_child_id_changes_when_segment_text_corrected`.

**Existing tests found:** `etl3/tests/test_enrichment.py` (names section, lines 794-898: alias extraction, `s/o`/`d/o`/`w/o` abbreviated-form extraction, surname `@`-alias stripping, exact-tiled duplicate collapse — 341-row evidence base per its own comment — hyphen-residue trimming) and `etl3/tests/test_multi_accused.py` (33 tests: numbered-pack detection, false-positive guards for initials/A-codes/phone digits/house numbers, non-sequential/duplicate/out-of-order marker rejection, `"and N others"` non-fabrication, shared-trailer address splitting, idempotent split-row building). This is genuinely solid regression coverage for the specific patterns it targets — the gaps below are patterns outside that target set, not failures of what's already covered.

## 5. Cleaning Rules Specification

Each rule below states the **current** regex/logic (file:line), the **gap**, and the **proposed** change. All proposed changes are additive/extending — none require removing or loosening an existing safety check.

**Numeric prefixes** (`etl3/enrichment/names.py:_strip_noise`, line 93): current pattern `^A-?\d+[)\.\s]+` only strips an `A`-prefixed code. Add a sibling pattern `^\s*0*\d{1,2}\s*[.)]\s+` for a bare list-number prefix with no `A`, applied **before** multi-person detection runs (so a single-marker record like `"02. Abid Ali..."` gets its prefix cleaned even though it never qualifies for a split).

**A-code colon variant** (same function): current pattern's character class `[)\.\s]` after the digit excludes `:`. Extend to `[)\.:\s]`.

**Accused numbering as split evidence** (`etl3/enrichment/multi_accused.py:_MARKER_RE`, line 42): currently excludes A-codes entirely. Proposed: a **second-tier** detector (new function, not a change to the existing one) that recognizes `A\d+` sequences the same way `_MARKER_RE` recognizes `N.`/`N)` — strictly sequential, no repeats, plausible segment content — but caps its result at `"low"` confidence (never `"high"`), so it only ever reaches the review queue, never auto-split. This directly targets the 23 A-code records currently invisible to any detection path.

**Marker punctuation variants** (`_MARKER_RE`): extend `[.)]` to `[.)]{1,2}` (or an explicit alternation) to catch `"N)."` numbering, and extend the pre-marker boundary to optionally accept a preceding name-like token followed by whitespace (not just `,`/`;`/newline/`"and "`), gated behind a plausibility re-check of the resulting segment so this doesn't start matching ordinary sentences — this is the riskiest single change proposed in this document and needs its own test matrix (§6) before being enabled.

**Relationship markers, spelled-out forms** (`etl3/enrichment/names.py:extract_relationship_info`, line 64): currently only `s/o`, `d/o`, `w/o`. Add `son of`, `daughter of`, `wife of`, `mother of`, `father of`, `c/o`/`care of`, `h/o` as additional pattern/relation-type pairs, reusing the exact same extraction shape. Add a **dangling-marker** rule: when the marker pattern matches but captures no following content (e.g., trailing `"S/o"` with nothing after it, as in C-1), strip the marker anyway rather than leaving it attached — don't require a captured relative name as a precondition for removing the marker itself.

**Relationship-only records** (new, cross-cutting with category J): when, after extraction, the *entire* remaining `cleaned_full_name` would be empty (e.g. `"Wife of Amzad"` → relation extracted, nothing left), do not fall back to the original raw string as the "name" (current `clean_full_name` guard does this) — instead set `cleaned_full_name=None` and `name_identified=False`, while still keeping `relation_type`/`cleaned_relative_name` populated.

**Nationality/country words in the name**: new function reusing `address.py`'s existing `NATIONALITY_TO_COUNTRY`/`_NAME_COUNTRY_NOISE` tables (don't duplicate the list) to strip a recognized nationality/country token from the *name* once `resolve_name_country` has already consumed it for domicile purposes — so the two stay in lockstep by construction rather than drifting as two separately-maintained lists.

**Occupation/role words in parentheses**: extend `_strip_noise`'s hardcoded 3-phrase parenthetical list to a proper word list (peddler, supplier, consumer, customer, dealer, transporter, financier, kingpin, driver, trafficker, etc.) matched case-insensitively inside `(...)`, followed by a whitespace-normalization pass (collapse to single spaces, trim) since removing a mid-string parenthetical routinely leaves a double space.

**Generic phone-number strip**: add a bare 10-digit (optionally prefixed with `+91`/`0`) Indian mobile-number pattern to `_strip_noise`, independent of the existing labeled patterns (`cell:`, `ph.no.:`, `✆`) — covering the unlabeled `"...-9959075757"` / `"...# 9007155796"` shapes confirmed in the data.

**Age phrase, spelled-out unit**: extend `yrs?` to `yr?s?|years?` in both age-related `_strip_noise` patterns.

**`r/o` with an intervening period**: extend `r/o\s+` to `r\/o\.?\s*` (mirroring the already-correct `s/o\.?`/`d/o\.?`/`w/o\.?` treatment) in both the `extract_relationship_info`-adjacent R/o strip and the N/o strip.

**Occupation label `Occ:`**: add a strip pattern parallel to the existing `caste:` one.

**Multi-`@`-alias chains** (`etl3/enrichment/names.py:extract_alias_from_name`, line 53): currently reads only `parts[0]` and `parts[1]` from `name.split("@")`. Fix to collect **every** non-empty part after the first as a distinct alias (joined or returned as a list), and fix `clean_person_names`'s fallback `construct_full_name` path so a `None`/empty primary name never gets re-prefixed with a literal `"@"` that then leaks into `cleaned_full_name` (confirmed bug, G-2/G-3).

**Spelled-out alias word** (`"Alias"`/`"A.K.A."`/`"Also Known As"`): new extraction mirroring `extract_alias_from_name`'s shape but keyed on these words instead of `@`, supporting chains (`"Alias"` can repeat, as in `"Ajay Alias Kittu Alias Bittu Kaleri"`).

**Invalid/placeholder literals** (new function, category J): exact-match (case-insensitive, trimmed) against `{-, n/a, na, unknown, unknown person, not known, not available, nil, none, null, .}` → `name_identified=False`. Run this check **first**, before any other cleaning stage, so a placeholder value never gets partially "cleaned" into something that looks more plausible than it is.

**Mojibake/encoding artifacts**: normalize common UTF-8-as-Latin-1 mis-decodes (stray `Â`, `�`) and smart-quote/en-dash punctuation to their plain-ASCII equivalents, as a display-normalization pass distinct from (and running after) all identity-bearing extraction above, so it never interferes with name-content decisions.

## 7. Deduplication Compatibility (read-only findings, no changes recommended)

- `etl3/identity/person_matching.py:load_persons()` matches on `persons_unified.full_name` (raw) + `relative_name` + `phone_number` — **not** `person_enrichment.cleaned_full_name`. Every fix proposed in §5/§6 touches only `person_enrichment`, so **none of them change matching behaviour, inputs, or thresholds** — confirmed by reading the full call path, not inferred.
- Occupation/nationality words currently embedded in raw `full_name` (e.g. `"Anil (Supplier)"`, `"Aisha (Nigerian)"`) *do* contaminate the `WEAK_CANDIDATE` exact-string tier (`_norm_name`+`_norm_name` equality) and partially blunt the `DETERMINISTIC` phone tier (`a_toks == b_toks` requires the noise tokens to match too, demoting a true match from 0.95 to 0.80 confidence when one side has the noise and the other doesn't) — this is a real, demonstrated interaction, but fixing it is a `persons_unified.full_name` data-quality question (upstream of ETL3 entirely, since that table holds the raw merged value) or a `person_matching.py` input-source question (switch to `cleaned_full_name`) — **both out of scope here per the explicit "do not change deduplication logic" constraint.** Recorded as a finding for a future, separate decision.
- Initials are preserved through the cleaning pipeline (confirmed: `A. Bhujangarao`, `A.R. Jai Shiva` pass through `clean_full_name` completely untouched) — so initial-based token matching is unaffected by anything in this audit.
- Aliases remain available for matching as a **separate** field (`cleaned_alias`) and are never merged into `cleaned_full_name` — except for the confirmed `@`-chain bug (G-2/G-3), where a stray `@` leaks into `cleaned_full_name` itself, which **would** corrupt token-based name matching for those specific rows (an extra `@`-prefixed token/garbled string where a clean name should be). This is the one finding in this section with a direct, demonstrated dedup-quality impact, and it's already covered by the proposed fix in §5/§6.
- Multi-person split produces **stable, deterministic** child `person_id`/`accused_id` values (confirmed via `split_child_id()` and the idempotency tests) — a rerun never produces a different id for the same segment text, so split children are safe inputs to the existing matching candidate generator once the split stage is enabled. No change needed here.
- No existing canonical identity is ever altered by anything audited here: `write_split_rows`/`UnifiedBatchWriter` only ever adds or updates rows keyed on deterministically-derived new ids, never touches the parent's own identity beyond setting `split_superseded_at` (confirmed by reading `accused_split.py` in full).

## 10. Implementation Roadmap

**Critical fixes** (small, isolated regex extensions; each independently testable; zero architectural change; directly fix confirmed, demonstrated bugs):
1. `@`-alias chain data loss + stray-`@` leak into `cleaned_full_name` (G-2/G-3) — this is the only finding in this audit that is an outright confirmed *bug* in already-shipped logic, as opposed to a missing capability.
2. A-code colon variant not stripped (`A-1:`).
3. `yrs?`→`year(s)?` and `r/o`→`r/o.?` regex-strictness fixes.
4. Invalid-literal detection (`name_identified` flag) extended to include status-word-as-name cases (`Absconding`, `Unknown Person`) — 0.24% of the dataset, the largest single quantified gap.

**High-priority improvements** (new, additive capability; no existing behaviour changes; each has a clear real-data justification from §3):
5. Bare numeric list-prefix stripping.
6. Spelled-out alias word (`Alias`/`AKA`) extraction — more common in this data (0.248%) than the already-handled `@` form (0.004%).
7. Spelled-out relationship phrases (`wife of`, `mother of`, etc.) + dangling-marker stripping + relationship-only-record disposition.
8. Generalized parenthetical role-word stripping (beyond the current 3 hardcoded phrases) + whitespace normalization.
9. `"N)."` marker-punctuation variant in `detect_multi_accused` (unlocks records like S.No. 10 with zero ambiguity).

**Medium-priority improvements** (require a review-queue mechanism to exist, or carry more inherent ambiguity):
10. A-code-as-split-evidence, capped at `low` confidence, review-only.
11. Nationality/country-word stripping from the name (reusing `address.py`'s tables) — correctly already separated from domicile classification, so this is purely cosmetic/display cleanup, not a correctness fix.
12. Non-exact duplicate-token soft-flagging (`review_flags`) without any rewrite.
13. Address-cross-check to suppress place-name false positives in the multi-person candidate queue (§4, `Hari, Nagulakatta Zaheerabad`).

**Future enhancements** (lower volume in this dataset, or dependent on decisions outside this audit's scope):
14. Space-separated (no-comma) numbered-list boundary extension in `_MARKER_RE` — highest payoff per-record (catches genuine 4-person records like S.No. 9) but also the highest false-positive risk of anything proposed here; needs its own dedicated test matrix before any implementation attempt.
15. Mojibake/encoding normalization (0.098% of records — real, but low volume).
16. `Alias`-column-specific parsing (comma lists, numbered prefixes inside that field) — same patterns as `Full Name`, lower volume (0.11%).
17. **Operational, not code:** apply migration `018_multi_accused_occurrences.sql` under its own review, then enable `ETL3_MULTI_ACCUSED_SPLIT_ENABLED=1` — the split logic for the clean numbered-pack case (B-1 style) is already correct and tested; it is simply switched off. This alone would start correctly splitting every record shaped like S.No. 4, 6, 8, 18 without any code change at all.
18. **Decision needed, out of scope here:** whether `person_matching.py:load_persons()` should read `cleaned_full_name` instead of raw `full_name` — flagged in §7 as a real coupling, explicitly not acted on per the "do not change deduplication logic" constraint.

Dependencies: items 1–9 have no dependencies on each other or on anything else and can land independently. Item 10 depends on a review-queue/UI concept existing somewhere downstream to be useful (otherwise it's a flag nobody reads) — worth confirming that exists before investing in it. Item 14 should not be attempted before items 2 and 5 are in place and stable, since its boundary-widening risk is easier to reason about once the simpler prefix-stripping noise is already out of the way. Item 17 is independent of all code changes above but should happen *after* at least the critical fixes, so split children are born already benefiting from the cleaner extraction.

## 11. Final Assessment

1. **How many distinct name-cleaning edge-case categories exist in the actual dataset?** 10 top-level categories (matching the brief's A–J), with 30+ distinct sub-patterns documented in §3, each with real `S.No.` evidence.

2. **Which edge cases are already handled by ETL3?** Single-alias `@`-extraction; abbreviated `s/o`/`d/o`/`w/o` extraction (when a relative name follows); exact whole-string duplicate-name collapse; hyphen-residue trimming; preservation of legitimate initials/prefixes (`Md.`, `A.R.`); high-confidence comma/`and`-bounded numbered-pack detection (`N.`/`N)` style only); non-fabrication of accused for `"and N others"`; shared-trailer address splitting for multi-person packs; ambiguous unnumbered comma/`&` lists correctly flagged (never auto-split); non-sequential/duplicate/out-of-order numbering correctly rejected.

3. **Which edge cases are not handled?** Bare numeric prefixes (no `A-`); A-code colon variant; A-codes as any kind of split evidence (even for review); `"N)."` punctuation; space-separated numbered lists; spelled-out relationship phrases; dangling relationship markers; nationality/country words in the name; most parenthetical role words (beyond 3 hardcoded phrases); unlabeled phone numbers; spelled-out ages (`years`); `Occ:` labels; spelled-out alias words (`Alias`/`AKA`) — the single largest-volume unhandled pattern at 0.248%; any invalid/placeholder-literal detection at all; mojibake/encoding artifacts; non-exact duplicate-token flagging.

4. **Which existing rules could cause incorrect person identities?** None of the *currently shipped* rules were found to produce an incorrect split or incorrect merge — the module's conservative design (cap ambiguous cases at `"low"`, never auto-split) holds up under direct testing against real data. The one confirmed correctness bug is the `@`-alias-chain issue (G-2/G-3), which corrupts a *name*, not an identity-matching decision (per §7, `cleaned_full_name` isn't read by matching). The main identity risk is not in what's shipped, but in *how any future fix is implemented*: widening `_MARKER_RE`'s boundary carelessly (item 14) is the one change in this roadmap that could plausibly cause a false split if implemented without its own dedicated test matrix.

5. **How many records potentially contain multiple accused persons?** At least 52 (numeric prefix) + 23 (A-code) + 14 (`&`) + 75 (bare `and`) + 75 (comma, name-like segments) = roughly 150–200 records show *some* multi-person signal before overlap removal; of these, only 13 are currently detected at `"high"` confidence by the shipped detector. §4's matrix shows at least 3 more real multi-person records (S.No. 9, 10, 68) that are unambiguous on inspection but currently invisible to detection entirely.

6. **How many records potentially contain aliases rather than multiple persons?** 127 records use the spelled-out `"Alias"`/`"AKA"` word in `Full Name` (currently 0% extracted); 2 use `@` in `Full Name` directly; 626 `Alias`-column values use `@`; the classic "comma list that's actually aliases, not persons" shape (S.No. 1: `Abid Ali, Altamas, Pradeep, Nandu, Uday`) exists but cannot be reliably counted separately from "genuinely multiple persons" by text alone — that ambiguity is exactly why the confirmed business rule requires leaving it unsplit.

7. **How many records are ambiguous and should remain unchanged?** At minimum the 75 "comma, name-like segments" + a portion of the 52 numeric-prefix records whose list content can't be confidently resolved to persons-vs-aliases (e.g. S.No. 1) — conservatively 100–130 records (≈0.2–0.25%) should stay untouched under the confirmed ambiguity rule, pending either more source evidence or human review.

8. **What is the safest architecture for implementing the improvements?** The existing 6-stage architecture proposed in the original brief (parse → multi-person detection → extraction → metadata → normalization → validation) is directionally correct and already partially realized in the current code's own separation of concerns (`multi_accused.py` detection is already decoupled from `names.py` extraction, which is already decoupled from `accused_split.py` writes). The one addition this audit recommends: insert an explicit **validation/invalid-literal stage *first***, before any extraction runs, so a placeholder value is flagged immediately rather than flowing through extraction logic that might coincidentally "clean" it into something that looks more legitimate than it is. Every new rule should ship as **additive** (new function, new flag, new confidence tier) rather than modifying an existing high-confidence code path in place — this is what has kept the shipped code's false-positive rate at effectively zero under direct testing, and should be preserved as the project's actual, de-facto design principle going forward, codified rather than just inherited by convention.

9. **Which database and ETL changes are required?** For the critical/high-priority fixes (§10 items 1–9): none — they are pure `names.py`/`multi_accused.py` logic changes feeding the existing `person_enrichment` columns, with one new boolean column (`name_identified`) and optionally one new text/array column (`unidentified_reason`, `review_flags`) via a new, additive migration. For item 17 (enabling the existing split stage): migration `018_multi_accused_occurrences.sql` must be applied (it is purely additive — nullable columns, one new table — and has not touched any existing row in review) before `ETL3_MULTI_ACCUSED_SPLIT_ENABLED=1` is set.

10. **What test coverage is needed before deployment?** The 33-case matrix in §8 (18 new, 15 regression) at minimum. Every `[NEW]` case must be added to `etl3/tests/test_enrichment.py` or `etl3/tests/test_multi_accused.py` (matching the existing file split by concern) *before* the corresponding fix lands, following this repository's own evident practice of real-data-derived regression tests with S.No./source-record provenance in the docstring. Items involving any confidence-tier or boundary change (A-code-as-evidence, space-separated boundary widening) additionally need the existing false-positive guard tests (`test_initials_not_mistaken_for_markers`, `test_accused_code_style_markers_not_split`, `test_phone_and_house_number_digits_not_mistaken_for_markers`) re-run and confirmed still passing, since those are exactly the tests that would catch a regression introduced by loosening the detector.

# CCTNS V2 API Historical Log Audit — Accused Record Changes & ETL Reconciliation

**Scope:** CCTNS V2 only (the `/accused` and `/person-details` endpoints and their downstream ETL3 processing). CCTNS V1 is mentioned only where it clarifies a V2 finding.
**Method:** Direct read-only SQL queries against the live `dopams_cctns_v2` database (via `etl3.db.connections.get_unified_connection(readonly=True)` and the project's own enforced-read-only `get_v2_source_connection()`), direct code reading of the ETL3 pipeline, and review of this project's own prior internal audit reports. No code, data, or configuration was modified. All personally identifying accused/person names are masked with initials; structural identifiers (FIR/crime/accused IDs) are kept because they are not personal data and are required for traceability.
**Status:** This document reflects the evidence available as of 2026-11-19. Where a claim could not be verified, it is marked **Inconclusive** rather than asserted.

---

## 1. Executive Summary

1. **The illustrative example in the task brief does not match current ETL behaviour.** An unnumbered, comma-separated name list — e.g. "Name A, Name B, Name C, Name D, Name E" with no numbering — is explicitly **never auto-split** by the current `detect_multi_accused()` detector (`etl3/enrichment/multi_accused.py`). It is flagged only as a low-confidence "candidate" for manual review. Only a *numbered* pack (`"1) Name, 2) Name"`) or an *accused-code* pack (`"A1. Name, A2. Name"`) is split automatically. This was verified both by running the detector directly against the literal example text and against a real CCTNS record containing that exact text (see §5, row "Combined → separate").

2. **Real combined-name splitting has happened in production, but it is overwhelmingly a V1 phenomenon.** As of this audit, 13 real parent accused records have triggered a high-confidence split, producing 32 real child records (`accused_split_audit`, live table). **12 of the 13 parents are CCTNS V1-sourced; only 1 is CCTNS V2-sourced.** That one V2 case (FIR `869/2026`, crime `6a359f414d1e611f530f007e`) is not a clean illustration of the brief's premise — it is evidence of a *deeper, pre-existing* CCTNS V2 data-quality pattern: the same FIR already had four separate, independently-coded CCTNS V2 accused records for what appear to be the same four people (reordered/misspelled name variants) **before** ETL3 ever touched it, and a *fifth*, uncoded accused record whose name field packed all four names together. ETL3's split then added a **third** representation of those same four people. See §8 for full detail — this is the single most load-bearing finding in this audit.

3. **CCTNS V2 record identity (ACCUSED_ID, PERSON_ID) is stable in the data observed so far.** Zero genuine reassignments of `accused.person_id` and zero genuine reassignments of `accused.crime_id` were found across 51,146 and 51,837 tracked V2 accused-field observations respectively. CCTNS V2 ids (Mongo-ObjectId-shaped strings) show no churn in this dataset, unlike CCTNS V1's documented MD5-style id churn.

4. **Genuine content changes do happen, and the project's own change-tracking table already distinguishes them from mere re-fetches.** 378 genuine `full_name` corrections and 11 genuine `alias` corrections were found for real V2 persons (word-order swaps, spelling fixes, alias additions). 1,197 genuine `accused_status` transitions (e.g. Absconding → "41A Cr.P.C issued", Absconding → "Arrest By Police") were found.

5. **The CCTNS V2 API itself exposes no structured deletion/inactive flag.** `ACCUSED_STATUS` is free text, not an enum, and no "is_deleted"/"is_active" field exists anywhere in the audited `/accused` or `/person-details` contract. See §6 and §9.

6. **No raw CCTNS V2 HTTP request/response logs survive on disk.** The legacy ETL's per-run log files (`cctns-v2/logs/*.log`) are not retained on this checkout. The only durable historical trail is ETL3's own append-only `accused_source`/`persons_source` tables, which capture snapshots of the **already-ingested Postgres row**, not the literal CCTNS HTTP response bytes, and which only cover 2026-09-25 through 2026-11-06 for V2 (see §2).

7. **A real, measurable "duplicate accused on the same FIR" pattern exists independent of the split feature**: 173 (crime, name) groups with more than one accused record sharing an identical name on the same V2 crime, 269 "excess" rows in total (one crime alone accounts for 82 of the duplicate rows — see §8). Most are plausibly coincidental common names; at least one (FIR 869/2026) is a verified genuine duplicate.

8. **None of this ETL3 work is visible to the live DOPAMS frontend today, and the raw-observation pipeline is currently stalled.** The migration meant to expose cleaned/split data through the backend read contract (`019_backend_read_contract_cleaned_names.sql`) was never applied (lost to a filename collision with an unrelated `019_drug_finding_status.sql`); the live frontend still reads the legacy `firs_mv`/`accuseds_mv` materialized views, consistent with this project's own cutover-readiness documentation. Separately, independently confirmed against `consolidation_run_log`: ETL3's raw-observation ("consolidation") step — the one that writes new rows to `accused_source`/`persons_source` — has had **no successful run since 2026-11-06**, 13 days before this audit. The 13 real split parents / 32 real split children (§7, §8) came from two one-off, manually-triggered backfill-script executions against the live database, not a continuously scheduled job, and the production **application** server is reported (by this project's own deployment report) to be running an older commit that predates the split feature entirely — so, regardless of the `ETL3_MULTI_ACCUSED_SPLIT_ENABLED=1` setting in this checkout's config, the feature is not actually active in the deployed production app. Everything in this report describes what the data and code demonstrably *do*, not what end users currently *see*.

## 3. CCTNS V2 API Record Structure

Confirmed against the project's own captured raw API samples (`cctns-v2/CCTNSV2_data/*.json`) and `cctns-v2_schema_mapping_report.md`:

**`GET /accused` / `GET /accused/{crimeId}`** — fields actually used: `ACCUSED_ID, CRIME_ID, PERSON_ID, ACCUSED_CODE, TYPE, SEQ_NUM, IS_CCL, PHYSICAL_FEATURES.*, ACCUSED_STATUS, DATE_CREATED, DATE_MODIFIED`. No field for a combined/packed name exists on the accused record itself — the name lives on the **linked person** record.

**`GET /person-details/{personId}`** — `PERSONAL_DETAILS.{NAME, SURNAME, ALIAS, FULL_NAME, RELATION_TYPE, RELATIVE_NAME, GENDER, DATE_OF_BIRTH, AGE, OCCUPATION, CASTE, NATIONALITY, ...}`, plus `PRESENT_ADDRESS`, `PERMANENT_ADDRESS`, `CONTACT_DETAILS`, `IDENTITY_DETAILS[]`, `MEDIA[]`, `DATE_CREATED`, `DATE_MODIFIED`.

Important, verified-from-a-real-sample nuance: **`FULL_NAME` is itself a CCTNS-computed composite**, not necessarily raw operator text. A real captured sample shows `NAME: "Yousuf "`, `ALIAS: "Party"`, `FULL_NAME: "Yousuf @Party"` — i.e. CCTNS already concatenates `NAME + "@" + ALIAS` into `FULL_NAME` for a single individual with an alias. The multi-accused detector's regexes do not treat `@` as a marker at all, so this correctly never gets misread as a multi-person pack — but it does mean a bare `@`-joined `FULL_NAME` is evidence of **one person's alias**, not of "combined and separate overlap." This distinction matters for anyone reviewing `FULL_NAME` text manually.

Other confirmed contract facts from `cctns-v2_schema_mapping_report.md`:
- Identity/contact fields use `""` (empty string) as CCTNS's own null-sentinel on the `accused` and `crimes` tables, not JSON `null`. A field being `""` is a normal observed state, not evidence of deletion.
- `ACCUSED_CODE`/`IS_ABSCONDING` can be entirely absent as JSON keys on roughly 3% of sampled `arrests`-endpoint records.
- No pagination cursor exists for `/accused`; the ETL instead chunks by `fromDate`/`toDate` in overlapping 5-day windows (`chunk_days=5`, `chunk_overlap_days=1`) to avoid missing boundary records — "pagination" in the CCTNS V2 sense means date-window chunking, not a page token.
- No endpoint or field anywhere in the audited contract represents an explicit delete/cancel/inactive flag. `ACCUSED_STATUS` is the closest analogue and is unstructured text (observed real values include `"Absconding"`, `"Arrest By Police"`, `"Arrest By Police and Remanded"`, `"41A Cr.P.C issued on DD/MM/YYYY"`).

## 4. Historical Accused Record Changes — How They're Detected

ETL3's merger computes, on every re-observation of a source record, a field-by-field diff against the previously-computed `*_unified` row, and writes one `change_log` row per changed field with `change_classification` set to one of:
- `initial_observation` — first time this record was ever seen (not a "change" in the business sense)
- `business_change` — the field's value genuinely differs from its previous value
- `etl_reobservation_no_diff` — the record was re-fetched but nothing changed
- `administrative_bulk_excluded` — reserved for the 2026-08-24-style bulk event, but **not actually used** (0 `bulk_event_exclusions` rows exist, so no row carries this classification in practice today)

This means every quantitative figure in this report that says "N genuine changes" is filtering on `change_classification='business_change' AND old_value IS NOT NULL AND old_value <> new_value` — i.e. a real old→new transition, not a NULL being filled in for the first time.

## 6. Source Identifier Analysis

- **`ACCUSED_ID`** (CCTNS V2): a MongoDB-ObjectId-shaped 24-hex-character string. Zero reassignment/churn observed across 34,449 distinct ids and 2,797 re-observed ids. Scoped to one accused-appearance-on-one-crime (verified: every `accused_unified` row for V2 has exactly one `crime_id`; no id was ever seen moving between crimes).
- **`PERSON_ID`** (CCTNS V2): same id format/stability characteristics. Confirmed to be an *accused-appearance* identity concept more than a verified cross-case "this is the same human" identity — ETL3 itself never auto-merges persons across sources (`identity_links` holds only human-reviewed candidate/confirmed/rejected matches, 1,171 rows, none auto-confirmed by any code path).
- **Implementation note on the unified PK format:** the design documents (`dopams_cctns/schema/ETL3_UNIFIED_SCHEMA.sql`, migration `001_initial_schema.sql`) state `accused_unified.accused_id` should be `source_system || ':' || source_record_id` for every row. In the live data, this holds for every V1 row (prefixed `V1:...`) but **V2 rows are stored with no `V2:` prefix at all** — `accused_unified.accused_id` for a V2 row is literally the bare CCTNS `ACCUSED_ID`, with `source_system='V2'` only in its own column. This is a real, verified inconsistency between the documented design and the live V2 adapter's behaviour (likely tolerated because V2's own ids never collide with V1's MD5-style ids), but it is worth flagging since the design doc's own stated rationale for the prefix ("accused_id ... is NOT a stable natural key across time") was written primarily about V1's churn, not V2's.
- **`DATE_CREATED`/`DATE_MODIFIED`:** present on both `/accused` and `/person-details`, ISO-8601 with `Z`. These are the only "last-touched" signal CCTNS V2 exposes; there is no separate "record version" or "revision number" field.
- **Explicit record status:** none, beyond free-text `ACCUSED_STATUS` (see §3, §5 row 15).

## 7. Current ETL Behaviour (code-verified)

- **Detection (`etl3/enrichment/multi_accused.py`):** conservative, pattern-based. Only a *strictly sequential, starting-at-1* numbered list (`"1) A, 2) B"`) or accused-code list (`"A1. A, A2. B"`) is classified `confidence="high"` and auto-split. An unnumbered comma/"and" list is `confidence="low"` and is **never** auto-split — only surfaced as a `candidate_segments` hint for manual review. Verified empirically: the task brief's own example text (an unnumbered 5-name comma list) returns `confidence="low"` from this exact code, and a real CCTNS record containing that identical text is confirmed (via this project's own prior internal audit) to remain unsplit "only as a side effect of the numbering gap, not because anything actually evaluated and deliberately deferred it."
- **Trigger and scope (`etl3/enrichment/runner.py`):** gated by `ETL3_MULTI_ACCUSED_SPLIT_ENABLED` (currently `=1` in this deployment's `etl3/config/.env`, with a comment stating it mirrors the production server's own setting). When enabled, `_multi_accused_split()` is one step in the fixed daily-pipeline step list and **re-scans every non-child `accused_unified` row on every run** (not an incremental/changed-only subset), re-reading each one's **current** `persons_unified.full_name` every time. This directly answers the audit's core reconciliation question: **a later correction to an already-split accused's name is re-detected and reconciled on the very next enrichment run** — this is not a one-time, never-revisited operation.
- **Correction/reordering semantics:** a split child's id is `sha256(parent_id | segment_index | normalized_text)[:24]` — deterministic, not random. If the text at a given segment position changes, the id changes; the old child is marked `split_superseded_at` (soft-retired, never deleted — its own `person_enrichment` row is preserved) and a new child is created. Reordering two segments is handled the same way (both old ids superseded, two new ids created) — the code's own docstring states this is deliberate: it never guesses "the same person moved" because that guess could hand one person's AI-derived enrichment to a different person.
- **Duplicate prevention:** `accused_split_audit` carries a unique index on `(parent_accused_id, segment_index) WHERE status='active'` — structurally prevents two simultaneously-active children at the same parent+position.
- **Parent handling:** once a parent produces a high-confidence split, it is marked `split_superseded_at` (idempotent — reproducing the same split on a later run does not touch the timestamp again) to stop it being re-offered to downstream AI enrichment, but the parent row itself is **never deleted**.
- **Real activity, but not continuous production operation:** 13 real parents / 32 real children exist in `accused_split_audit` today (cross-checked directly against the live table by this audit, independent of the project's own prior report, and the two counts agree). Two runs produced them: 2026-10-24 (16 children, all V1) and 2026-11-18 (16 children, 12 V1 + 4 V2 — the FIR 869/2026 case) — but both were **one-off, manually-triggered backfill-script executions** against the live database, not a continuously scheduled job, and this project's own deployment report states the production **application** server is running an older commit that predates the split feature, so it is not active there regardless of the `.env` flag in this checkout (see Executive Summary, point 8).
- **A dedicated diagnostic script** (`etl3/diagnostics/_validate_multi_accused_split.py`) exercises re-run idempotency, name-correction, reordering, shared-trailing-address, and "and N others" scenarios — but against a **disposable, hard-coded-forbidden-from-touching-production database**, not real CCTNS data. Its results are code-proof of designed behaviour, not production evidence, and are cited in §9 only as "Confirmed (implementation)," never as "Confirmed (historical)."
- **Name cleaning (`etl3/enrichment/names.py`) and splitting never conflict**, because they read/write disjoint columns: `persons_unified.full_name` stays the raw CCTNS text forever; cleaned output goes to a separate `person_enrichment.cleaned_full_name` column, and the split detector always parses the raw column.

## 8. Duplicate and Data Integrity Findings — FIR 869/2026 in Detail

This is the single confirmed real CCTNS V2 case of the client's described scenario, and it is more informative than a clean example would have been, because it reveals a problem the client's premise did not anticipate.

**CCTNS crime `6a359f414d1e611f530f007e`, FIR `869/2026`, narcotics-adjacent case, status "Absconding" on the packed record.** Nine `accused_unified` rows exist for this one crime today:

| Accused ID (masked suffix) | Accused code | Status | Origin | Name (masked) |
|---|---|---|---|---|
| `...2c` (parent) | *(blank)* | Absconding | Native CCTNS V2 record | `"1). [P1], 2). [P2], 3). [P3], 4). [P4]"` — four names packed with explicit numbering |
| `...2c:split:...` ×4 | *(n/a — ETL3-generated)* | *(inherits parent)* | **ETL3-derived**, created 2026-11-18 | `[P1]`, `[P2]`, `[P3]`, `[P4]` individually |
| `...4e0` | CCL*(juvenile code)* | 41A Cr.P.C issued 20/06/2026 | **Native CCTNS V2 record**, independent of the pack | `[P3-variant]` — same person as P3, tokens reordered and one letter substituted |
| `...9b1` | A2 | 41A Cr.P.C issued 20/06/2026 | **Native CCTNS V2 record**, independent of the pack | `[P2-variant]` — same person as P2, given/family-name order swapped |
| `...fad` | A1 | 41A Cr.P.C issued 20/06/2026 | **Native CCTNS V2 record**, independent of the pack | `[P1-variant]` — same person as P1, with an extra token and letters transposed |
| `...bc6` | A4 | 41A Cr.P.C issued 20/06/2026 | **Native CCTNS V2 record**, independent of the pack | `[P4-variant]` — same person as P4, given/family-name order swapped |

What this means:
1. **Before ETL3 ever processed this FIR, CCTNS V2 itself already carried the same four people twice** — once properly coded (`A1`, `A2`, the CCL code, `A4`, status "41A Cr.P.C issued") and once combined into a single uncoded "Absconding" record. This is a genuine CCTNS V2 source-data duplication, not an ETL artifact — the independent `A1`/`A2`/CCL/`A4` records and the combined record all carry a real CCTNS `ACCUSED_ID`.
2. ETL3's split logic, which has no way to recognize that a pack's segments already match existing accused on the same crime, **added a third representation** (4 more rows) on top. The net effect of running the current split feature on this FIR is 9 live-looking accused rows for what is almost certainly 4 real people.
3. This is exactly the "combined and separate overlap" scenario from the task brief (row 10) — directly confirmed — but the practical lesson is different from the brief's framing: the risk is not that our own ETL invents duplicates from a single clean source record; it's that **CCTNS V2's own source data was already duplicated**, and the current split feature has no cross-check against a crime's existing accused roster before creating more rows. See §10, recommendation 1.

**Separately, FIR (masked), narcotics case, `case_status='UI'`:** 82 of that crime's accused records all carry the literal person name "absconding" (lowercase, used as if it were a name). Each has a distinct `accused_id`/`person_id` and a blank `accused_code`; two other accused on the same crime have real `accused_code`s as high as `A112`, implying this is a genuinely large case with well over 100 accused, of which 82 slots were apparently filled with the status word in place of a name rather than left blank. This matches, but is somewhat larger in this one case than, the system-wide figure of 150 V2 persons flagged `unidentified_reason='invalid_literal'` by ETL3's own enrichment — the discrepancy was not fully reconciled in this pass and should be checked (possibly the enrichment step hasn't re-run over every historical row, or applies a narrower literal-matching rule than a human reviewer would).

**System-wide:** 173 (crime, name) duplicate-name groups exist among V2 accused (excluding the enrichment-step gap above), 269 excess rows. Most are very likely coincidental common first names belonging to different real people (e.g., two different crimes each having one accused named a common short nickname) rather than true duplicates — only FIR 869/2026 was manually confirmed as a genuine duplicate in this pass; a full manual review of the remaining 172 groups was out of scope for this audit.

**Correction (2026-11-20, during the follow-on implementation task):** the "discrepancy" language above is wrong and is retracted. A direct query against `person_enrichment` shows all 82 "absconding"-named accused on this one FIR already have `name_identified=false, unidentified_reason='invalid_literal'` — they are a **subset** of the system-wide 150 V2 `invalid_literal` count (82 of 150, with the remaining 68 spread across other FIRs), not a second, unreconciled bucket competing with it. There was never a real discrepancy to investigate; the two numbers were simply being compared as if they were independent totals when one is a subset of the other. See `DOPAMS_ETL3_ACCUSED_RECONCILIATION_IMPLEMENTATION_REPORT.md` section 5 for the verification query.

## 9. Confirmed, Not Observed, and Inconclusive Scenarios — Summary

**Confirmed (real CCTNS V2 evidence exists):** Name correction; Alias changes; Duplicate names; Same names/different IDs; Combined-and-separate overlap; Unknown/blank names as a standing state; Source-ID changes (ETL3-side only, not CCTNS-side).

**Not Observed (checked, no occurrence found):** Accused removed from a crime; Name replacement via person-link reassignment; Partial/incomplete API responses; Same accused/person under multiple FIRs; Unknown/blank names arising via an in-place transition.

**Inconclusive (data cannot establish the answer):** Combined→separate as an *in-place transition* for the same record (only single-snapshot coverage exists so far); New-accused-added-over-time (confounded by the 2026-08-24 bulk administrative event).

**Not Supported by API:** Explicit deletion/cancellation/inactive status.

No scenario in this list is being called impossible — each "Not Observed"/"Inconclusive" line states exactly what was checked and what the limiting factor is, per the task's own instruction.

## 10. Recommended ETL Reconciliation Rules

1. **Before auto-splitting a packed name, check the crime's existing accused roster for near-duplicate names.** FIR 869/2026 (§8) shows the current split logic has no such check and can triple-represent the same people. A practical rule: compute a normalized-name similarity between each parsed segment and every *other* non-split accused already on the same `crime_id`; if a strong match exists, route to manual review instead of auto-creating a new split child.
2. **Treat `ACCUSED_STATUS` free text, not a dedicated field, as the only deletion/lifecycle signal**, and do not expect CCTNS V2 to ever send a structured delete — any "record removed" reconciliation logic must be inferred from absence in a complete re-fetch, not from a flag.
3. **Populate `bulk_event_exclusions`** for the already-documented 2026-08-24 window (and audit for any other similar bulk-touch events) so that `change_log`'s own `administrative_bulk_excluded` classification — which exists in the schema but is never actually used today — starts doing the job it was designed for. Until this is done, any date-driven timeline analysis against this data must manually exclude that window, as this report had to.
4. **Reconcile the `V2:` prefix inconsistency** (§6) — either apply it to V2 the same way it's applied to V1, or formally document why V2 is the one exception, since a future reader of the schema's own comments will otherwise be misled.
5. **Investigate the discrepancy between the 82-row single-FIR "absconding" placeholder count and the system-wide 150-row `invalid_literal` enrichment count** (§8) — determine whether the enrichment step has a backlog or a narrower matching rule than manual review found.
6. **Extend historical coverage before drawing firmer conclusions.** The real append-only trail is six weeks old and currently not growing (consolidation has not run successfully since 2026-11-06 — see §2); several of this report's "Inconclusive" findings (new-accused-over-time, in-place combined→separate) would become answerable with the pipeline restarted and another few months of `accused_source`/`persons_source` accumulation, uncontaminated by one-off bulk events.
7. **Decide, explicitly, whether to close the production gap described in Executive Summary point 8** — apply (or correctly re-number) the stalled `019_backend_read_contract_cleaned_names.sql` migration, deploy the commit that contains the split feature to the actual application server, and restart the consolidation schedule — before relying on any of this analysis for client-facing behaviour, since none of it reaches the live frontend today.
8. **Prioritize the still-open items on this project's own name-cleaning roadmap** (`DOPAMS_ETL3_NAME_CLEANING_EDGE_CASE_AUDIT.md` §10) that remain unbuilt as of this audit: bare nationality-word stripping, widening marker-boundary detection to space-separated (no-comma) numbered lists, a human review-queue UI for the "low confidence" candidates this report's §7 describes as never auto-split, and alias parsing specific to the spelled-out "Alias"/"AKA" form (127 legacy records, more common than the `@` form — see §5 row 9). The "critical" and "high-priority" items on that same roadmap (1-9, plus enabling the split flag) were already implemented and executed against live data on 2026-11-18, per that report's own companion validation/deployment reports.

Is the FIR 869/2026 pattern (independently-coded accused *and* a combined-pack accused for the same people, on the same crime) a known CCTNS V2 data-entry behaviour (e.g., an investigating officer manually adding a "wanted/absconding summary" entry alongside the properly coded ones), or is it itself a CCTNS-side defect worth raising with the CCTNS provider?
